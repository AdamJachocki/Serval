# Design

## Context

See `proposal.md` for motivation and the specs under `specs/deployment/` and
`specs/web/network-listener/` for required behavior.

Current state relevant to the approach:

- `deploy/install-identity.sh` and `deploy/validate-web-identity.sh` already
  implement identity creation, validation, `agent.json` generation and unit
  installation, as root, from the repository checkout. The units are written to
  `/etc/systemd/system`.
- The units expect `/opt/serval/agent/Serval.Agent` and
  `/opt/serval/web/Serval.Web` and run Web as `serval-web` with
  `ASPNETCORE_ENVIRONMENT=Production`.
- Agent validates `/etc/serval/agent.json`, `/etc/pam.d/serval`, `/run/serval`
  and `/var/lib/serval` at startup and refuses to run on unsafe state
  (`src/Serval.Agent/AgentConfiguration.cs`). The paths and modes are listed in
  `docs/identity-deployment.md`.
- Web uses ASP.NET Core defaults for its listener, always calls
  `UseHttpsRedirection`, and calls `UseHsts` outside Development. The
  development compose fixture sets `ASPNETCORE_URLS=http://0.0.0.0:8080`.
- Both projects already declare `linux-x64` and `linux-arm64` runtime
  identifiers. CI already publishes self-contained test hosts and runs
  real-systemd tests on Ubuntu 22.04/24.04/26.04 runners and a Debian 13
  systemd container, for both architectures.
- SQLite is bundled through `SQLitePCLRaw.bundle_e_sqlite3`; PAM is loaded from
  the host's `libpam`.

## Goals / Non-Goals

**Goals:**
- One package build per architecture that installs on every supported release.
- Maintainer scripts that reuse, not re-implement, the existing identity
  validation rules.
- No new privileged capability in Agent and no new dependency in the .NET
  projects.
- Every lifecycle path (install, upgrade, failed upgrade, remove, purge,
  reinstall) and `serval-setup` verified against real systemd in CI.

**Non-Goals:**
- Per-release package builds or distribution-specific binaries.
- Automatic certificate renewal. A self-signed certificate is regenerated by
  running `serval-setup listen` again.
- Managing firewalls, reverse proxies or port 443 redirection.

## Decisions

### D1. Build the package with `dpkg-deb` from a staged tree

A repository script publishes Agent and Web self-contained for the target
runtime, stages the package tree with explicit ownership and modes, writes
`DEBIAN/control`, the maintainer scripts and the debconf templates, and runs
`dpkg-deb --root-owner-group --build`. CI runs `lintian` on the result.

- *Alternative: debhelper (`dpkg-buildpackage`).* Canonical for the Debian
  archive, but it is built around compiling from a source package and does not
  fit a self-contained .NET publish without considerable overrides. Archive
  submission is a non-goal.
- *Alternative: nfpm.* Produces `.deb` from YAML, but adds a third-party build
  tool for a single output format. `dpkg-deb` is already on every Debian and
  Ubuntu runner.

### D2. Filesystem layout

| Path | Owner | Notes |
| --- | --- | --- |
| `/opt/serval/agent/`, `/opt/serval/web/` | root, not writable by others | self-contained publish output; unchanged from today |
| `/usr/lib/systemd/system/serval-{agent,web}.service` | root `0644` | package-owned units; admins override through drop-ins in `/etc` |
| `/etc/pam.d/serval` | root `0644` | dpkg conffile |
| `/usr/sbin/serval-setup` | root `0755` | D6 |
| `/usr/lib/serval/serval-common.sh` | root `0644` | shared validation and atomic-write functions, sourced by maintainer scripts and `serval-setup` |
| `/etc/serval/agent.json` | root `0600` | generated, not a conffile (D4) |
| `/etc/serval/web.json` | root:`serval-web` `0640` | optional; written only by `serval-setup` |
| `/etc/serval/tls/` | root:`serval-web` `0750` | `cert.pem` `0644`, `key.pem` root:`serval-web` `0640` |
| `/var/lib/serval/backups/<version>-<UTC timestamp>/` | root `0700`, files `0600` | D5 |

`/opt` stays because the units, the docs and the F5 fixture already use it and
FHS allows add-on packages there. The units move from `/etc/systemd/system`
(admin territory) to the vendor unit directory, which is where a package must
place them. The unit names do not change, so the privileged-unit exclusion in
`docs/serval-privileged-unit-exclusion.md` keeps applying.

`deploy/install-identity.sh` remains for source deployments but sources the
same `serval-common.sh` from the repository, so validation rules exist once.

### D3. Maintainer scripts

All scripts are POSIX `sh` with `set -eu`, take no input other than dpkg's
arguments and debconf answers, and call fixed executables with separately
quoted arguments.

```text
 install:  preinst(install) -> unpack -> postinst(configure)
 upgrade:  preinst(upgrade) [stop web, stop agent, backup] -> unpack
           -> postinst(configure) [keep config, start agent, start web]
 failed upgrade: dpkg runs old postinst(abort-upgrade) -> restart old services
 remove:   prerm(remove) [stop web, stop agent] -> postrm(remove) [disable]
 purge:    postrm(purge) [rm /etc/serval, /etc/pam.d/serval, /var/lib/serval-web; keep /var/lib/serval]
```

`postinst configure` on a fresh install: validate that the protected paths are
not symbolic links; create `serval-web` with `adduser --system --group
--no-create-home --home /nonexistent --shell /usr/sbin/nologin`; run the shared
identity validation; resolve the debconf group; write `agent.json` atomically;
`systemctl daemon-reload`; enable both units with `deb-systemd-helper`; start
Agent and then Web with `deb-systemd-invoke`. If Agent does not become active,
the script fails and does not start Web.

Starting services is ordered explicitly instead of relying on dpkg's helpers'
default ordering, because Web `Requires=` Agent and Agent must pass its startup
checks first.

### D4. Host-admin group through debconf, `agent.json` as generated state

A debconf `string` question `serval/admin-group` (priority `high`, default
`sudo`) is asked in `config` and read in `postinst`. Under
`noninteractive` the default or preseeded value is used. `dpkg-reconfigure
serval` and `serval-setup admin-group` share one function that validates the
group and rewrites `agent.json`.

`agent.json` is created by `postinst` only when absent; upgrades leave it alone.
It is not a dpkg conffile because its content depends on the host's UIDs and
GIDs. Rewrites use `jq` with `--arg`/`--argjson` to preserve unknown-to-the-
script fields such as `idleMinutes`, then write to a temporary file in
`/etc/serval`, set mode and owner, and `mv` into place.

- *Alternative: hand-built JSON with `printf`, as today.* Works for creation but
  cannot preserve an administrator's `idleMinutes` on rewrite without parsing.
- *Alternative: implement `serval-setup` in .NET.* Gives typed parsing but adds
  another self-contained runtime copy or couples setup to Agent. Agent must stay
  minimal and must not gain a host-configuration mode.

### D5. Upgrade backup

`preinst upgrade` stops Web and then Agent, then copies `policy.db` and any
`-wal`/`-shm` companions into a new `/var/lib/serval/backups/<old-version>-<UTC
timestamp>/` with `cp --preserve=mode,ownership` and verifies the copies with
`cmp`. With Agent stopped the file copy is consistent, matching the procedure in
`docs/identity-deployment.md`. Any failure exits non-zero, so dpkg aborts the
upgrade before unpacking and calls the old `postinst abort-upgrade`, which
restarts the old services. The five newest backup directories are kept.

Implementation must confirm that Agent's `/var/lib/serval` validation accepts the
extra `backups` directory; if it does not, backups go to
`/var/backups/serval/` with the same modes instead. Either location is
root-only and preserved by purge.

### D6. `serval-setup` as a root-only shell command

`serval-setup` is a POSIX `sh` script that refuses to run unless the effective
UID is 0, parses a fixed grammar (`listen`, `admin-group`, `status`), validates
every value before use, and uses the shared atomic-write function. It is a local
administration tool, like `dpkg-reconfigure`; it is not reachable through Web or
the Agent socket and does not change the Agent IPC contract.

- Addresses must parse as literal IPv4 or IPv6 addresses; host names for
  self-signed certificates must match a DNS label grammar or be IP literals;
  ports are 1024 to 65535.
- Self-signed certificates are generated with `openssl req -x509` using an
  ECDSA P-256 key, SANs from `--hostname`, and 365-day validity.
- Operator certificates are opened with `O_NOFOLLOW` semantics (checked with
  `test -L` plus `test -f` and copied with `install`, not followed), validated
  with `openssl x509`/`openssl pkey` for parse, expiry, unencrypted key and key
  match, then copied into `/etc/serval/tls/`.
- Before writing, the current `web.json` and TLS files are saved to a
  temporary root-only directory. After a restart the script waits for the unit
  to become active and for the port to accept a connection; on failure it
  restores the saved files and restarts again (spec: atomic and recoverable
  changes).

Restarting Serval's own units here is the explicit purpose of the command; it is
unrelated to the managed-service rule that saving and restarting are separate
operations, which governs services administered through Serval.

### D7. Web listener configuration

In the `Production` environment Web:

1. Opens `/etc/serval/web.json` if present, rejecting symbolic links, non-root
   owner, group other than `serval-web`, or any write bit for group or others
   (same checks pattern as `AgentConfiguration`, implemented in Web because Web
   does not reference Agent).
2. Deserializes a strict shape `{ "address", "port", "tls": { "certificate",
   "key" } | null }`, rejecting unknown fields, non-literal addresses, ports
   outside 1024 to 65535, and TLS paths outside `/etc/serval/tls/`.
3. Configures Kestrel with an explicit `Listen` endpoint, which replaces
   `ASPNETCORE_URLS`, `--urls` and `Kestrel` configuration sections. Absent
   file means `127.0.0.1:9080` HTTP.
4. Refuses to start when the address is not loopback and TLS is absent.
5. Enables `UseHttpsRedirection` and `UseHsts` (one year) only when TLS is
   configured. Today's unconditional `UseHttpsRedirection` has no HTTPS port
   to redirect to on loopback HTTP and only logs a warning.

Port 9080 is chosen to avoid the commonly occupied 8080 and 5000.

`Development` and `Testing` keep the current behavior so the F5 fixture and
`WebApplicationFactory` tests are unaffected.

### D8. Package dependencies

`Depends:` `adduser, debconf, init-system-helpers, systemd, libpam0g,
libpam-runtime, openssl, jq, libicu78 | libicu76 | libicu74 | libicu72 |
libicu70, libssl3t64 | libssl3`. The ICU and OpenSSL alternatives cover the
package names across the supported releases (OpenSSL was renamed for the 64-bit
time transition). The exact list is confirmed by installing into minimal images
of every supported release in CI; anything the self-contained runtime loads that
is missing there is added.

- *Alternative: `InvariantGlobalization=true` to drop ICU.* Removes the
  fragile alternatives list but changes culture-sensitive behavior in Web.
  Deferred until someone confirms Web does not depend on culture data.

### D9. APT repository and bootstrap

- **Hosting:** GitHub Pages of the Serval repository, serving
  `install.sh`, `serval-archive-keyring.gpg` and `apt/`. No third-party package
  host.
- **Repository:** one suite `stable`, component `main`, architectures `amd64`
  and `arm64`, because the package is identical across releases. Built with
  `apt-ftparchive` from the `.deb` assets of all GitHub Releases, so earlier
  versions stay available. `InRelease` and `Release.gpg` are signed with an
  RSA 4096 release key.
- **Key handling:** the private key is stored as a secret of a protected GitHub
  `release` environment that requires maintainer approval; only the
  tag-triggered release workflow can use it. The public key is published
  dearmored, and `install.sh` pins its SHA-256, so a substituted key file is
  rejected without needing `gpg` on the host.
- **Client configuration:** `install.sh` writes the keyring to
  `/usr/share/keyrings/serval-archive-keyring.gpg` and a deb822 source
  `/etc/apt/sources.list.d/serval.sources` with `Signed-By:`.
- **Script safety:** the whole script body is inside a function called on the
  last line, so a truncated download runs nothing. It checks root, `/etc/os-release`
  (`ID`, `VERSION_ID`) and `dpkg --print-architecture` before any change.

### D10. Versioning and servicing

The package version is the release tag without the `v` prefix. The bundled
runtime version is written to a `Serval-Dotnet-Runtime` control field (shown by
`dpkg -s serval`) and to the package changelog. Dependabot gains the
`dotnet-sdk` ecosystem so SDK and runtime servicing updates arrive as pull
requests; the release checklist in the new packaging document requires a
package release after merging one that fixes a runtime security issue.

### D11. Tests

- **Web unit tests:** default listener, valid HTTPS configuration, unsafe file
  ownership/mode/symlink, unknown field, out-of-range port, TLS path outside the
  TLS directory, non-loopback without TLS, environment and `Kestrel` override
  ignored in Production, Development unchanged.
- **Package tests (real systemd):** a script run in systemd containers for
  Debian 13, Ubuntu 22.04, 24.04 and 26.04, on `amd64` and `arm64` runners. It
  covers every scenario in `deployment/debian-package` and
  `deployment/host-setup`, including the negative ones (unsafe pre-existing
  account, symlinked paths, invalid or preseeded group, forced backup failure,
  Agent startup failure after upgrade, port already in use, invalid
  certificates, non-root `serval-setup`, malformed arguments). Upgrade tests
  install a package built with a lower version first.
- **Bootstrap tests:** `install.sh` against a locally served signed test
  repository with a throwaway key, plus unsupported-release, non-root, key
  hash mismatch and truncated-script cases.
- **Static checks:** `lintian` on the package, `shellcheck` on all shell code.

## Risks / Trade-offs

- [Bundled runtime receives security fixes only when we release] → Dependabot
  `dotnet-sdk` updates plus the release checklist; package metadata shows the
  runtime version so administrators can check.
- [ICU and OpenSSL package names change in a future release] → alternatives in
  `Depends`, verified per supported release in CI; adding a release requires
  adding it to the CI matrix first.
- [Self-signed certificates teach users to click through warnings] → it is an
  explicit choice in `serval-setup`, the fingerprint is printed for
  out-of-band verification, and operator certificates are supported.
- [Secure cookies over `http://localhost` are not honored by every browser,
  notably some Safari versions] → the loopback mode targets SSH tunnels from
  Chromium and Firefox, which treat localhost as a secure context; the docs name
  this limitation, and HTTPS through `serval-setup` is the alternative.
- [`curl | sh` is distrusted by some administrators] → the same steps are
  documented for manual execution, and `.deb` files with checksums are attached
  to every release.
- [Release key compromise would let an attacker publish packages] → key usable
  only in an approval-gated environment; the packaging document describes key
  rotation (publish new key, update the pinned hash, ship a package that
  installs the new keyring).
- [Package-owned units move from `/etc/systemd/system` to the vendor directory]
  → hosts installed with the old script have stale copies in `/etc` that would
  shadow the package units; `postinst` detects byte-identical copies of the
  old units and removes them, and otherwise fails with an explanation.

## Migration Plan

1. Hosts installed from source with `install-identity.sh`: install the package.
   `postinst` finds the existing `serval-web`, validates it, keeps an existing
   `agent.json`, handles the old unit copies as above, and makes a backup of the
   existing database before starting the packaged binaries. The previous
   `/opt/serval` trees are replaced by the package contents.
2. Rollback of a package upgrade follows the existing procedure in
   `docs/identity-deployment.md`: stop both services, restore the backup
   directory created by `preinst`, and install the previous version with
   `apt-get install serval=<version>`.

## Promote to permanent documentation

- Package layout, maintainer-script behavior, the release key, repository
  hosting and the servicing obligation: a new `docs/packaging-and-release.md`.
- Web listener rule (Production: loopback HTTP by default, non-loopback only
  with TLS): `ARCHITECTURE.md` runtime boundaries and `SECURITY.md`.
- Supported versions and update channel: `SECURITY.md` "Supported versions".
- Package-first install, `serval-setup` and the TLS directory paths:
  `docs/identity-deployment.md`.

## Open Questions

- Whether to put the repository and `install.sh` behind a custom domain before
  the first public release. A domain can be introduced later by publishing the
  same content there; existing clients would need a one-time source update, so
  it is cheapest to decide before the first release.
